Add complete 2Factor.in SMS/OTP integration to KhanaLagao for mobile OTP login, signup verification, 2FA, password reset, staff invite verification, and SMS campaigns.

Official docs:
2Factor API Postman docs:
https://documenter.getpostman.com/view/301893/TWDamFGh

2Factor website/pricing/API overview:
https://2factor.in/v3/sms-api
https://2factor.in/

Important:
- Do not break existing login/authentication.
- Do not break existing SMS provider architecture.
- Do not break existing email OTP, WhatsApp OTP, or password login.
- Add 2Factor.in as one SMS/OTP provider inside Super Admin Provider Center.
- All 2Factor API keys must be configured only in Super Admin.
- Restaurant admin must not see or edit 2Factor API keys.
- Restaurant admin can only enable/disable SMS OTP/SMS campaigns if Super Admin and plan allow it.
- Use real 2Factor APIs, not mock success.
- If 2Factor is not configured, show proper configuration error.
- OTP must be secure, rate-limited, expiring, and logged.
- Do not store OTP in plain text.
- Build this for web and mobile app both.

Feature name:
2Factor.in SMS & OTP Provider

====================================================

Create provider adapter:

TwoFactorSmsProviderAdapter

Methods:
- sendOtp({ mobile, countryCode, purpose, templateName })
- verifyOtp({ sessionId, otp })
- resendOtp({ sessionId })
- sendTransactionalSms({ mobile, message, templateName })
- sendPromotionalSms({ mobile, message, templateName })
- sendVoiceOtp({ mobile }) if supported
- testConnection()
- normalizeError(error)
- getBalance() if API supports

Important:
- Keep 2Factor logic only in provider adapter/service.
- Do not write 2Factor code directly inside React components.
- Frontend should only call internal KhanaLagao APIs.
- Backend should call 2Factor APIs.

====================================================
5. 2FACTOR API ENDPOINT STRUCTURE
====================================================

Use 2Factor API documentation to implement exact endpoints.

Common 2Factor OTP flow normally has:
1. Send OTP to mobile number.
2. Receive session/details ID from provider.
3. Verify OTP using session/details ID + OTP.

Implement endpoints using official docs:
- Send OTP API
- Verify OTP API
- Transactional SMS API
- Promotional SMS API if enabled
- Voice OTP API if enabled
- Delivery report/status API if available

Important:
- Follow exact endpoint format from 2Factor docs.
- Support both auto-generated OTP by 2Factor and custom OTP mode if docs/provider support it.
- Store provider session/details ID for verification.
- Do not trust frontend verification.

====================================================
6. INTERNAL AUTH API FLOW
====================================================

Use existing auth APIs or create these:

POST /api/auth/request-otp
POST /api/auth/verify-otp
POST /api/auth/resend-otp
POST /api/auth/login-password
POST /api/auth/verify-2fa
POST /api/auth/register/start
POST /api/auth/register/verify-mobile
POST /api/auth/register/complete

When channel = sms and provider = 2factor:
- Use 2FactorSmsProviderAdapter.

POST /api/auth/request-otp input:
{
  "identifier_type": "mobile",
  "country_code": "+91",
  "mobile_number": "9876543210",
  "purpose": "login_mobile",
  "channel": "sms"
}

Backend:
1. Validate mobile number.
2. Check Super Admin settings.
3. Check rate limits.
4. Check purpose allowed.
5. Create otp_verification record.
6. Call 2Factor Send OTP API.
7. Store provider session/details ID.
8. Return safe response.

POST /api/auth/verify-otp input:
{
  "identifier_type": "mobile",
  "country_code": "+91",
  "mobile_number": "9876543210",
  "purpose": "login_mobile",
  "otp": "123456"
}

Backend:
1. Find latest pending OTP record.
2. Verify OTP with 2Factor if provider verification is used.
3. Or verify locally if using custom OTP mode.
4. Mark verified.
5. Complete login / signup / 2FA / password reset based on purpose.
6. Create session/JWT only after valid verification.
